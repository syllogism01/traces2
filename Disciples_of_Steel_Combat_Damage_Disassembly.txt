Disciples of Steel — Combat Damage Reverse-Engineering Record
Executable: STEEL(10).EXE
Purpose: LLM handoff / continuation of a byte-level disassembly of the combat damage routine

STATUS AND METHODOLOGY
======================

This document records the executable-backed findings established so far. It deliberately separates:
  1. exact assembly/data facts,
  2. algebraic reconstructions that follow directly from those instructions,
  3. gameplay-facing interpretations supported by direct evidence,
  4. unresolved links.

Physical EXE offsets and runtime segment:offset addresses must not be conflated.

The resident image has an MZ header with e_cparhdr = 0x2BC, so ordinary resident-image physical conversion is:
    physical = image_offset + 0x2BC0

The executable is 759404 bytes (0xB966C).

Blinker overlays are present. In particular:
    blCOMBAT1 ~ physical 0x2C5F0
    blCCOMBAT ~ physical 0x7706A
    blCOMBAT2 ~ physical 0x7C46C
    blCOMBAT3 ~ physical 0x9D808

Runtime far addresses such as 1E11:xxxx, 0853:xxxx, or 0000:3D6E must not be converted to physical offsets by the ordinary +0x2BC0 rule. Blinker vector slots are resolved/managed at runtime.

EXECUTIVE DAMAGE PIPELINE
=========================

The currently proven chain is:

    encoded combat/source record
             |
             v
        handler/case 51
             |
             v
       decode source chars
             |
             v
          116A[1..8]
             |
             +---- combat calculations use fields 3, 5, 6, 8
             |
             v
           0344
             |
             v
          BP-2E / BP-6C
             |
             v
       damage-table lookup
             |
             v
           [0286]
             |
             +---- 02E4 / 02E6 modifier stage
             |
             v
           [0286]
             |
             v
      target state -= [0286]

The final target-state mutation is proven at physical 0x7EF27:

    7EF27: MOV BX,[02D0h]
    7EF2B: SHL BX,1
    7EF2D: MOV SI,183Eh
    7EF30: MOV DX,BX
    7EF32: ADD BX,[SI+0Ah]
    7EF35: MOV ES,[SI+02h]
    7EF38: MOV AX,ES:[BX]
    7EF3B: SUB AX,[0286h]
    7EF3F: MOV BX,DX
    7EF41: ADD BX,[SI+0Ah]
    7EF44: MOV ES,[SI+02h]
    7EF47: MOV ES:[BX],AX

Therefore, if:
    target_value = WORD indexed by 2*[02D0] in descriptor 183E

then:
    target_value_after = target_value_before - WORD [0286]

There is no arithmetic/call between the SUB and the store.

The next check is:

    7EF4A: MOV BX,DX
    7EF4C: ADD BX,[SI+0Ah]
    7EF4F: MOV ES,[SI+02h]
    7EF52: CMP WORD PTR ES:[BX],0
    7EF56: JLE 7EF62

So the updated target value is immediately tested for <= 0.

DAMAGE VALUE PRODUCER: WEAPON/COMBAT TABLE LOOKUP
==================================================

At physical 0x305A4:

    305A4: MOV WORD PTR [0286h],0000h

    305AA: MOV AX,[BP-16h]
    305AD: IMUL WORD PTR [BP-30h]

    305B0: MOV SI,[BP+0Ch]
    305B3: ADD AX,[SI]

    305B5: SHL AX,1
    305B7: MOV BX,AX

    305B9: LEA SI,[BP-28h]
    305BC: ADD BX,[SI+0Ah]
    305BF: MOV ES,[SI+02h]
    305C2: MOV AX,ES:[BX]
    305C5: MOV [BP-38h],AX

This gives:

    index_word = [BP-16] * [BP-30] + WORD PTR [[BP+0C]]
    byte_offset = 2 * index_word
    D = WORD PTR [descriptor at BP-28 + byte_offset]
    [BP-38] = D

For the normal-damage path, [BP+0C] has been observed as 01F6, giving:

    D = WORD in ES_0102 at:
        descriptor0102.offset + 2*([BP-16]*[BP-30] + 01F6)

This selected table value is NOT the final damage. It is the parameter used by the random accumulation below.

RANDOM ACCUMULATION INTO [0286]
================================

The loop around 305DE is:

    305DE: MOV AX,[BP-3Ah]
    305E1: MOV [BP-36h],AX
    305E4: MOV AX,0001h
    305E7: JMP 30601

    30601: MOV [BP-2Ah],AX
    30604: CMP AX,[BP-36h]
    30607: JLE 305EAh

    305EA: LEA AX,[BP-38h]
    305ED: PUSH AX
    305EE: LCALL 0000:3E32
    305F3: MOV [BP-3Ch],AX
    305F6: MOV AX,[BP-3Ch]
    305F9: ADD [0286h],AX

The exact loop semantics are:

    for i = 1 .. [BP-3A]:
        R = RandomHelper(&[BP-38])
        [0286] += R

The initial selected table value D is passed by pointer to 3E32.

3E32 RANDOM/ROLL HELPER
=======================

Resident routine at physical 0x69F2:

    69F2: MOV CX,0002h
    69F5: LCALL 1348:536Dh
    69FA: PUSH 42C8h
    69FD: PUSH 0000h
    69FF: LCALL 1348:2CDE
    6A04: MOV SI,AX
    6A06: INT 35
    6A07: DB 04h
    6A08: MOV SI,[BP+06h]
    6A0B: INT 3Ah
    6A0C: DB 0Ch
    6A0E: INT 3Dh
    6A10: DB 9Ah, A6h, 00h, 4Bh, 12h
    6A15: INT 34h
    6A16: DB 06h, CEh, 3Eh
    6A19: INT 3Bh
    6A1A: DB 5Eh, ECh
    6A1C: INT 3Dh
    6A1E: MOV AX,[BP-14h]
    6A21: LCALL 1348:53A4
    6A26: LRET 0002h

The INT bytes are the compiler's x87-emulation instruction stream. Decoded conceptually, the key operations are:

    FLD DWORD PTR [SI]        ; generated random float
    MOV SI,[BP+06h]
    FIADD WORD PTR [SI]       ; + D
    LCALL 124B:00A6           ; unresolved normalize/round operation
    FADD DWORD PTR [3ECE]     ; + constant
    FISTP WORD PTR [BP-14h]
    MOV AX,[BP-14h]

Thus:

    R = FISTP( Normalize(RandomFloat + D) + constant[3ECE] )

The exact semantics of 124B:00A6 and the constant's runtime numeric value are unresolved.

C06 FINAL DAMAGE FORMULA
========================

At physical 0x306E2:

    306E2: FILD WORD PTR [0286h]

    306E7: MOV SI,116Ah
    306EA: MOV BX,0006h
    306ED: ADD BX,[SI+0Ah]
    306F0: MOV ES,[SI+02h]
    306F3: MOV AX,ES:[BX]
    306F6: SHL AX,1
    306F8: MOV BX,AX

    306FA: MOV SI,0C06h
    306FD: ADD BX,[SI+0Ah]
    30700: MOV ES,[SI+02h]

    30703: FIMULS WORD PTR ES:[BX]
    3070E: LCALL 124B:00A6
    30713: FADD DWORD PTR SS:[41DCh]    ; +1.0

Then:

    3071F: FILD WORD PTR [0286h]
    30724: MOV AX,[02E6h]
    30727: IMUL WORD PTR [0286h]
    3072B: LCALL 124B:001Eh
    30730: FWAIT
    30732: LCALL 124B:00A6
    30737: FADDP ST(1),ST(0)
    3073A: FISTP WORD PTR [0286h]

Therefore:

    I = Normalize( [0286] * C06[116A[3]] ) + 1
    FINAL = I + Normalize( I * 02E6 )
    [0286] = FINAL

where the exact C06 indexing is:

    index = 2 * 116A[3]

and the C06 value is a WORD.

The normalization routines are still not semantically named beyond their observed role.

[BP+06] IN THE COMBAT ROUTINE
=============================

The combat function repeatedly dereferences [BP+06]:

    MOV SI,[BP+06h]
    MOV BX,[SI]
    SHL BX,1
    ...

It is also passed intact to another far routine:

    7E59B: PUSH WORD PTR [BP+06h]
    7E59E: LCALL 0B89:2D7Ah

And the 0344 builder uses it:

    91CB: MOV SI,[BP+06h]
    91CE: ADD AX,[SI]

Thus:

    U = WORD PTR [[BP+06h]]

is a combatant/unit index in the 0EB8 lookup.

This strongly supports interpreting [BP+06] as a pointer to a combatant/unit-related structure, but the exact gameplay-facing name is not yet proven.

The target 0853:2CD2 is unresolved and must not be flattened into a physical EXE offset.

Another invocation:

    915E: MOV SI,116Ah

116A POPULATION HANDLER: CASE TABLE ENTRY 51
============================================

A crucial structural discovery is that 0x5B62 is NOT reached by an ordinary static CALL.

The physical table at 0xADD00 is a monotonically increasing table of code offsets. Entry 51 is:

    ADD00 + 2*51 = ADD66
    WORD[ADD66] = 5B62

The table begins:

    ADD00: DW 56E0
    ADD02: DW 5705
    ADD04: DW 570E
    ADD06: DW 5728
    ADD08: DW 5739
    ...
    ADD60: DW 5B00
    ADD62: DW 5B0E
    ADD64: DW 5B13
    ADD66: DW 5B62
    ADD68: DW 5B75
    ADD6A: DW 5B7E
    ADD6C: DW 5B83
    ADD6E: DW 5B8C
    ADD70: DW 5B91
    ADD72: DW 5B9F
    ADD74: DW 5BB0
    ...
    ADDDA: DW 620B
    ...
    ADDEE: DW 6401

There is no static CALL targeting 5B62. There is also no discovered static instruction that directly embeds the physical 0xADD00 address as an immediate table pointer.

Therefore the exact:
    selector -> dispatcher -> ADD00 -> 5B62
link remains unresolved.

This must be investigated through runtime/descriptor-style references rather than by inventing a simple JMP [ADD00+BX].

The executable elsewhere contains genuine computed jump tables, for comparison:

    1CBDB: CMP BX,0006h
    1CBDF: SHL BX,1
    1CBE1: JMP CS:[0185h+BX]

and:

    1F284: MOV BL,CH
    1F286: AND BX,001Fh
    1F289: SHL BX,1
    1F28B: JMP CS:[07A2h+BX]

and:

    20612: MOV DX,BX
    20614: MOV BL,[SI+0Bh]
    20617: SHL BX,1
    20619: JMP CS:[0882h+BX]

A runtime function-pointer dispatch example:

    167AF: MOV CX,[BX]
    167B1: MOV SI,[BX+02h]
    ...
    167C7: MOV AL,[SI+03h]
    167CA: NEG AL
    167CD: CBW
    167CF: SHL AX,1
    167D2: PUSH DI
    167D3: MOV DI,AX
    167D5: MOV DI,CS:[06E2h+DI]
    167D7: XCHG AX,DI
    167D8: CALL AX
    167DA: POP DI

These examples prove the executable uses indirect dispatching, but do not prove they are the 0xADD00 dispatcher.

====================

At 0x5B62:

    5B62: MOV CX,0090h
